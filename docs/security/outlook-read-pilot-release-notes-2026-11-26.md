# Isolated Outlook read pilot — release candidate notes

Candidate base: live CRM commit `dea8c63c3b299918c423dbb62b754cc5e5e39ced`; mailbox source: `9aebcfe317540363d42a7aed8a8b7f9a753040aa`. Outlook files were selected explicitly, not the source tree as a whole. The existing Exposé and HEIC feature, its public files, CSP and Vercel configuration remain those of the base. No deployment or live configuration is implied.

The candidate pins the independently identified public production Microsoft app client ID `0c00e270-a9c7-473e-baa2-3400058e8375`; rotating that registration requires a separately reviewed code change. It adds separate verified Microsoft mailbox authentication, read-only permission checks, personal-session binding, private mailbox synchronization and project-scoped contact review. Projectless contact hints are private suggestions from already imported copies, not verified replies. An explicit server action to add reviewed addresses to a suppression list was excluded; the API rejects it and the UI offers no such control. No automatic objection recording or sending capability is introduced by this pilot. Before any campaign send, objections and permissions still require a separate reliable process.

Migrations 212 and 213 are manual cutovers. Planning checks pinned sources, exact checksummed predecessor ledger entries, and historical mailbox identity aliases. This preparation is not permission to execute the migrations. The current runtime-role target query found the intended Neon project, branch, database and role, but returned `binding_ready=false` because the 212 identity objects were absent. No production migration was executed. Actual ledger, role/ACL/RLS and definition verification, recovery, build provenance, Microsoft app registration and real mailbox authentication/renewal remain separate release gates. Synthetic tests do not establish those gates.

The focused test chain is `npm run test:microsoft-federated`; CI calls it and it calls `test:mailbox-deployment-boundary`, the migration-lineage checks, the HTTP exclusion test and artificial mailbox/UI tests. Tests use fakes or local metadata; they do not establish live provider, tenant isolation or backup/restore behavior. The separate historical DB fixture with company-specific predecessor seeds is not in the chain. Broader existing CI, an actual production build and an end-to-end CRM connection have not been executed for this candidate.

In `verified-production`, configure the server-only `NOVALURE_MICROSOFT_MAILBOX_PILOT_SCOPE` for the exact pilot. The JSON object binds `workspaceId`, `actorId`, `microsoftTenantId`, `microsoftObjectId`, `projectId` and a distinct list of up to 100 `contactIds`. Select and verify the 100 roster entries under current CRM project access before any activation. Configuration is separate from mailbox consent and scheduling. The eligible actor must connect personally, enable private contact review, and use the contact check. The general manual import and filing endpoints are denied for the Microsoft pilot. The provider's read permission allows inbox metadata screening; only currently unique visible matches on the reviewed project and contact list qualify for private content storage. The import start time is preserved on reconnection, and contact eligibility and sender agreement are checked after provider I/O. No unrelated message is placed in the durable pending queue; successful pages retain the opaque provider continuation. A delayed or invalid page must be retried rather than reported as checked. Matching an address does not verify the sender, establish a campaign reply, record an objection or authorize sending.

## Inherited calendar finding — separate from the mailbox change

The existing live calendar code can fall back to its configured ambient global Microsoft token when a workspace-specific calendar is unavailable. A synthetic regression from the development branch (`scripts/microsoft-client-auth-tests.ts`, test `an unavailable workspace calendar never falls back to an ambient global token`) failed on this live-based candidate: it observed one fallback invocation where zero was expected. This code path existed in the base and was not changed for the Outlook read pilot. The finding is a potentially high-impact cross-workspace calendar isolation risk **if** the ambient token is actually configured and reachable for an affected request; this local test does not establish whether it is configured or whether a real request is exploitable. No real service was contacted. It needs separate owner/security triage and a verified fix or independent evidence that the ambient fallback is disabled before relying on that calendar integration. The failing inherited calendar test is intentionally not represented as passed by the Outlook-only chain.
