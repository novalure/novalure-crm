# Studio voice booking authority — isolated donor, 8 November 2026

This additive donor is based on CRM release candidate `d49be3e20f6c18f82571ca4bb257e43c44f0fec3`, in branch `codex/studio-crm-voice-authority-20261108`. It changes no coordinator worktree, dependency, lock, workflow, global status or masterplan. The only package metadata change appends the two targeted suites to the existing `test:booking:channels` command, which the existing CI already executes. It is not a release, migration installation, native gate result or real booking. The CRM coordinator retains integration, schema installation and all live effects.

## Connected boundary

The existing `POST /api/integrations/booking/voice` selects one complete authentication path using a bounded untrusted JWT audience selector. The new fixed `urn:novalure:crm:studio:voice-booking:production` audience selects its own RS256/JWKS verifier; the existing general audience retains the original machine handler. Unknown/array audiences, invalid claims and failed verification never fall back to another identity. Both paths still need their own current saved database authority. The new path grants only session, availability, hold, confirm and status. It cannot cancel, reschedule, resume a Studio chat session or extend the voice deadline.

The Studio verifier pins the existing production Vercel workload issuer, owner, project and subject, with a separate audience and logical identity `NOVALURE_STUDIO_VOICE_BOOKING`. `STUDIO_VOICE_AUTH_ENABLED=1` is only a technical kill switch; it grants no principal, booking scope, calendar access or production activation. The actual route injects no options. Tests may use the existing server-controlled verifier/pool/provider seams; neither caller fields nor headers can select those dependencies.

`verifyStudioVoiceBookingAuthority` always invokes the restricted database lookup after cryptographic verification. SQL consumes the already verified claim tuple, as the existing CRM authentication bootstrap does; SQL itself does not validate JWT signatures. The returned five metadata fields select the Studio workspace, actual saved principal/grant, publication and one type. Body fields cannot choose workspace, bot, publication, calendar or organizer. The existing `dispatchTrustedBookingTool`, opaque channel token stored as a hash, hold/confirm operation records, summary consent, idempotency and status reconciliation remain the booking engine. The Vapi bridge separately encrypts its durable state; this donor does not change that storage.

## Draft installation contract

`migrations/drafts/studio-voice-booking-authority.sql` is deliberately outside the automatic numbered migration stream. It requires existing migrations 108/109/111/112 and the authorized owner of `booking_channel_authorize_session` and the tables on which it creates policies/triggers. It installs no rows. New `studio_voice_principals` and `studio_voice_booking_grants` are separate from the historical synthetic-only principal table. No historical synthetic row or generic task identity is relabeled.

The principal and independently installed grant default disabled and expire using the real database clock. The grant binds the exact workspace, bot, publication/revision, assignment/type, organizer, Microsoft connection/revision, account, writable calendar, Teams support and production activation/origin. It also requires the bot's current independent `config.booking` grant and existing calendar production eligibility. Disabled/revoked/expired principals or grants, a disabled bot booking grant or bots module, and ineligible publications, connections or activations deny. The chatbot UI status is not a substitute for this independent booking grant. Actual resource IDs, costs, commercial rights and authority references must come from the responsible coordinator; this donor invents none.

Runtime has no table or column access to either new authority table and cannot install, edit, revoke or reactivate its own authority. Both tables use FORCE RLS. Private fixed-Studio policies permit the migration owner to evaluate and administer these rows without BYPASSRLS; narrowly scoped owner read policies cover the existing referenced objects. Public functions have fixed search paths. The authentication lookup exposes no credential, recipient, provider token or calendar detail.

The same authorized migration owner has explicit fixed-Studio INSERT/UPDATE policies for installing and controlling these two authority tables; no application role receives those rights. Every binding field, validity window and authority reference is immutable after INSERT. Enabled/kill controls may stop or resume a still-valid, unrevoked row, while a recorded revocation cannot be cleared or re-enabled. DELETE/TRUNCATE cannot remove these tombstones for same-ID reinsertion. A different resource needs a separately installed new grant ID with the prior row disabled/revoked; at most one enabled grant per principal prevents ambiguous lookup. Existing sessions retain their original IDs and cannot silently follow the replacement. The fixed principal identity remains globally unique: actor or principal-validity rotation is deliberately outside this narrow donor and needs a separately reviewed coordinator contract; no generic rotation engine is added. The draft seeds none of these rows.

The draft adds a `studio_voice` relation and a BEFORE INSERT/UPDATE session trigger. It checks current principal/grant/resource bindings inside the actual session transaction, including a revocation after the initial authority lookup. A failure rolls back the session and budget write. Existing Studio session scope, token, grant, creation time and original deadline are immutable; counters cannot decrease. No ended/expired-session, replacement session or confirmation retry path is added. Terminal revocation remains possible while unresolved original operations remain fenced.

Only the short `booking_channel_authorize_session` function gains an explicit Studio branch. The existing `booking_channel_upstream_allowed` implementation and every legacy/chat/form branch remain unchanged. The existing engine calls current authorization during claim and immediately before provider effects; the Studio branch rechecks its actual saved grant and calendar bindings there. Unknown hold/confirm results continue through original session and booking/idempotency keys, with no second creation. After the original voice/session deadline, use the coordinator's separately qualified read-only reconciliation process; do not renew the session.
