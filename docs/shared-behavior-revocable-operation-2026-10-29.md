# Explicit revocable operation for the existing shared-runtime bindings

Source-only successor to CRM54 (`54ae1c9d5269d4d76e7005315aef7e5fd7ed5054`). No production migration, binding conversion, deployment, provider change or model call is performed by this change. Migration119 was unused in the local tree and fetched `origin/main` (`93f44285`) at preparation time; recheck the live ledger and remote immediately before rollout.

## Stored meaning and preserved authorization

Both existing binding tables gain `operating_mode`, default `bounded`. Existing expiry values, flags, revocations, identities, cap hashes and grants are not updated. `bounded` requires a finite non-null `expires_at`. `revocable` requires `expires_at IS NULL`; it means no artificial binding end date, with all existing explicit revocation and current authority checks still mandatory. Unknown modes, NULL bounded dates, finite revocable dates and infinity are rejected by constraints. Personal `not_before` remains mandatory, including its existing comparison for bounded rows.

Only the six binding time comparisons in the existing five resolver functions change. Function OIDs, signatures, security-definer owners, search paths and ACLs are retained by `CREATE OR REPLACE`. Existing SHARE locks, FORCE RLS, tenant/actor/broker/bot checks, private actor compartments and knowledge grants remain. The old machine principal's own `not_before`, `expires_at`, state, kill switch and revocation checks are unchanged, even when its runtime binding is revocable. Nothing makes customer service actors able to log in or read business/knowledge data.

No runtime TypeScript change is necessary: the existing resolver return shapes contain no expiry, and all existing callers continue to use the same functions. The server configuration map, capability values and OIDC issuer/audience/project/environment/JTI checks remain unchanged. Short-lived OIDC credentials still require fresh normal issuance; revocable binding mode is not a token-lifetime override. Personal host policy/model-budget limits and genuine contract/module/entitlement/source-grant withdrawals remain separate stops. The current Knowledge entitlement schema does not provide a contract-end date; an external contract is not inferred to last forever.

## Own stop and rollback

Explicit stop continues to set only the owned `enabled=false`, preserving current revocation, mode, null/shortened expiry and identities. Existing historical operators that require Nov17 dates must not be relabeled or reused: their narrowly bound successor must recognize the new own conversion audit, accept legitimate later revocation, and impose no active policy/window/contract/grant gate on removing its own flags.

A data rollback is a separate admitted, one-attempt owner transaction. Lock the same five rows and own conversion audits; require the exact owned transition and current identities/cap hashes. Restore only `operating_mode='bounded'` and each audit's original finite expiry, preserving current flags/revocation and all other fields; append compensating audits. If that original expiry has passed, access remains denied; do not substitute a later date. Conflicting reassignment or unknown state requires read-only reconciliation, not overwrite.

A schema rollback requires **all** rows in both tables to be safely bounded with finite non-null expiry, including any independently provisioned rows. Otherwise keep119 installed and use a forward correction. Under that guard, restore the original five117/118 function definitions, enforce `expires_at NOT NULL`, and only then remove the119 constraints/columns in one atomic owner transaction. Preserve all audit history and qualify any ledger action through the existing migration operator. No destructive or automatic down-migration is shipped.
